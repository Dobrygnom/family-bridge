# Family Bridge: архитектура системы

## 1. Цель

Family Bridge — локально-ориентированная система, в которой два персональных AI-агента самостоятельно обсуждают отношения своих владельцев, используя их личную психологическую историю, но не передавая исходные архивы друг другу.

Основной режим полностью автоматический:

1. Family Bridge регулярно синхронизирует выбранный владельцем чат через локальный Codex app-server.
2. До подключения локальный Codex выделяет людей и готовит черновики тем, отдельно определяя, о ком тема и с кем её предлагается обсуждать.
3. Владелец исправляет маршрутизацию и явно разрешает подходящие темы; перекрёстные темы требуют особенно заметного подтверждения.
4. При подключении владелец выбирает, какого человека из его контекста представляет второй компьютер.
5. В пару попадают только разрешённые темы, адресованные выбранному человеку. Каждая тема запускается как отдельный параллельный диалог агентов.
6. После разговора каждый владелец получает персональный итог; при необходимости создаётся общий итог.

Система не является заменой лицензированного психолога. При признаках угрозы жизни, насилия, преследования или иной непосредственной опасности агент прекращает автономный разбор и рекомендует обратиться к человеку-профессионалу или экстренной службе.

## 2. Границы платформ OpenAI

- Локальный `codex app-server` предоставляет официальный протокол `thread/list` и `thread/read`, которым пользуется Family Bridge.
- Выбор источника выполняется в UI по проекту и названию чата; скрытый thread ID пользователю не нужен.
- Codex CLI используется как локальный агентный runtime с авторизацией через подписку ChatGPT, командами `codex exec` и `codex exec resume`.
- OpenAI API не нужен и в базовую архитектуру не входит.
- Отдельная задача Codex Desktop и браузерная выгрузка для синхронизации не нужны.

## 3. Компоненты

### 3.1. In-app Context Sync

Встроенный фоновый компонент Family Bridge на каждом компьютере.

Обязанности:

- показать в UI список доступных проектов и чатов;
- сохранить явно выбранный source thread ID вместе с видимыми проектом и названием;
- выгрузить только исходные текстовые реплики владельца, без ответов агента;
- атомарно заменить локальную выгрузку при смене источника;
- обновлять контекст при запуске, каждые шесть часов и по запросу владельца;
- показывать источник, количество реплик, время и статус синхронизации;
- выделять локальных людей и черновики тем до подключения;
- хранить для темы отдельно `aboutPersonIds` и `discussWithPersonId`;
- требовать явного разрешения темы до её передачи;
- не передавать личный архив во внешний транспорт.

### 3.2. Local Family Bridge

Фоновое кроссплатформенное приложение с автозапуском, системными уведомлениями и полноценным UI.

Обязанности:

- проверять установку и авторизацию Codex CLI;
- запускать и возобновлять закреплённую CLI-сессию семейного агента;
- читать локальный тематический индекс;
- поддерживать realtime-соединение с транспортом;
- надёжно принимать, подтверждать и отправлять сообщения;
- обеспечивать state machine разговора и turn token;
- хранить локальный журнал, темы, ограничения и отчёты;
- автоматически восстанавливаться после перезапуска.

Технологии:

- Electron для Windows/macOS: больший размер установщика принимается ради прямого переиспользования проверенного Node.js orchestration core;
- React + TypeScript для UI;
- Node.js main process для системного трея, автозапуска, локального состояния и запуска Codex CLI;
- атомарный локальный JSON-store для состояния прототипа (с возможностью перехода на SQLite при росте данных);
- Supabase Postgres + Realtime для production-транспорта;
- встроенный локальный transport для разработки и демонстрации.

### 3.3. Codex Agent Runtime

Для каждого владельца создаётся отдельная постоянная Codex CLI-сессия.

Первый запуск:

```text
codex exec --json --output-schema agent-response.schema.json <bootstrap prompt>
```

Последующие реплики:

```text
codex exec resume --json --output-schema agent-response.schema.json <session-id> <prompt>
```

Агент возвращает строго структурированный результат:

- `message_to_peer` — безопасная реплика второму агенту;
- `topics` — новые или изменённые темы;
- `owner_report` — персональный итог;
- `shared_report` — допустимый общий итог;
- `needs_owner_input` — действительно неразрешимый вопрос;
- `conversation_status` — continue, complete, paused или unsafe;

### 3.4. Realtime Transport

Production: Supabase Realtime и таблицы Postgres.

Транспорт не запускает модель и не видит локальные архивы. Он хранит только:

- зашифрованные межагентные сообщения;
- состояние сессии;
- предложения тем и ограничения, предназначенные для общего контура;
- подтверждения доставки;
- зашифрованные общие итоги.

Каждая установка аутентифицируется отдельно. Доступ ограничивается Row Level Security парой участников. Publishable key допустим в приложении; service-role key никогда не включается в клиент.

После связывания устройств создаётся общий симметричный ключ. Содержимое сообщений шифруется локально до отправки. Сервер видит метаданные доставки, но не текст.

Development: локальный WebSocket/HTTP relay с тем же интерфейсом транспорта. Он позволяет поднять два процесса на одном компьютере и проверить полный цикл без облачного аккаунта.

## 4. Локальная память

```text
memory/
├── context-source.json
├── context-analysis.json
├── style-samples.jsonl
└── disclosure-policy.md
```

- `context-source.json` — выбранный thread ID, видимые проект/название, время, количество реплик и статус синхронизации.
- `context-analysis.json` — найденные люди и локальные черновики тем с субъектом, адресатом, уровнем чувствительности и разрешением владельца.
- `style-samples.jsonl` — исходные реплики владельца базового чата; стиль по ним определяет само приложение.
- `disclosure-policy.md` — запреты на цитирование, раскрытие и конкретные темы.

Семейный агент получает релевантные фрагменты через локальный retrieval, а не весь многомесячный transcript на каждом ходе.

## 5. Протокол разговора

### 5.1. Состояния

```text
idle
  → proposing
  → agenda_negotiation
  → active
  → synthesizing
  → completed
```

Дополнительные состояния: `paused`, `waiting_peer`, `waiting_owner`, `unsafe`, `cancelled`.

### 5.2. Подготовка и запуск

До подключения найденные темы остаются локальными черновиками. Владелец проверяет «о ком», выбирает «обсудить с» и явно разрешает передачу. При создании пары старые темы другой пары не переносятся. После подключения темы обоих участников объединяются, а кнопка «Обсудить все темы» запускает по одному независимому диалогу на тему. Неудачно запущенная тема возвращается в очередь.

Ручная тема создаётся из UI только для уже выбранной пары.

### 5.3. Handshake и повестка

Перед содержательным разговором агенты обмениваются:

- идентификатором протокола и версией;
- поддерживаемыми возможностями;
- предложенными темами без личных исходных материалов;
- ограничениями раскрытия;
- максимальным числом ходов и временем сессии.

Повестка фиксируется серверным состоянием. Один `turn_token` принадлежит только одному агенту, поэтому оба агента не отвечают одновременно.

### 5.4. Надёжная очередь

Каждое сообщение содержит:

- уникальный `message_id`;
- `conversation_id`;
- `sequence_number`;
- отправителя и получателя;
- тип сообщения;
- зашифрованный payload;
- timestamp и срок жизни;
- статус `pending`, `claimed`, `processed`, `failed`;
- idempotency key.

Получатель атомарно claim-ит сообщение, вызывает Codex, отправляет ответ и только затем подтверждает исходное сообщение. После сбоя сообщение возвращается в очередь. Повторная доставка безопасна благодаря idempotency key.

### 5.5. Остановка

Разговор заканчивается при одном из условий:

- оба агента считают цель достигнутой;
- достигнут лимит ходов или времени;
- разговор перестал приносить новую информацию;
- требуется ответ владельца;
- обнаружен запрещённый или небезопасный контекст;
- пользователь поставил паузу.

## 6. Итоги

После каждой сессии формируются:

- персональный отчёт Диме;
- персональный отчёт Кате;
- общий нейтральный отчёт, если его публикация допустима;
- точки согласия и расхождения;
- возможные неверные интерпретации;
- конкретные следующие шаги;
- вопросы, которые агенты не смогли разрешить.

Персональный отчёт остаётся только локально. Общий отчёт передаётся зашифрованным.

## 7. UI

При первом запуске вместо соединения показывается обязательный мастер: выбор базового чата, видимый ход выгрузки и анализа, затем проверка тем. Реестр тем группируется по предполагаемому собеседнику и рассчитан на десятки и сотни строк: компактная строка содержит разрешение, название, «о ком» и раскрытие; объяснение, маршрутизация и предупреждение появляются только в раскрытом состоянии. Есть фильтр спорных тем и массовое разрешение безопасных прямых тем.

После завершения мастера основной экран содержит только два рабочих блока: «Соединение» и «Темы для этой пары». В «Соединении» пользователь выбирает, кого представляет второй компьютер, создаёт приглашение или вводит полученный код. В «Темах» видит общую очередь и одну кнопку «Обсудить все темы».

Дополнительные разделы:

- «Контекст» — выбранный проект/чат, найденные люди, поля «О ком» и «Обсудить с», явное разрешение каждой темы;
- «Итоги» — сохранённые отчёты;
- «Настройки» — имя владельца, автозапуск, обновления и запрещённые темы.

Режимы разработки и локальная имитация двух участников не показываются в пользовательском UI.

Интерфейс локализован на русский, английский, чешский и французский; выбранный язык сохраняется локально.

## 8. Установка

Установка инициируется одной инструкцией `INSTALL_FOR_CODEX.md`, загруженной в Codex Desktop.

Codex Desktop:

1. определяет ОС и архитектуру;
2. проверяет Git и Codex CLI;
3. устанавливает отсутствующие prerequisites поддерживаемым способом;
4. клонирует репозиторий GitHub;
5. устанавливает подписанное приложение;
6. проверяет `codex login status` и при необходимости запускает официальный login;
7. создаёт локальную структуру памяти;
8. предлагает выбрать базовый чат прямо в UI и выполняет первую синхронизацию;
9. проверяет автоматическое и ручное обновление контекста;
10. связывает устройства через одноразовый код/QR;
11. выполняет self-test без чтения личного содержания.

## 9. Этапы реализации

1. Локальный headless demo: два отдельных Codex CLI agent session, надёжная очередь, turn token и итог.
2. Общий TypeScript core и тесты протокола.
3. Electron UI и background/autostart.
4. Supabase schema, RLS, Realtime и E2E encryption.
5. Встроенный выбор и периодическая синхронизация базового чата через Codex app-server.
6. Установщики Windows/macOS и GitHub release.

Критерий успешного demo: два независимо настроенных агента автоматически проводят ограниченный разговор через локальный transport, не отвечают одновременно, завершают сессию и создают два персональных отчёта и общий итог.
